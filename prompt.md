# dbt Analytics Engineer Prompt

Install once:

```bash
npx skills add zohaibRT/agentic-dbt-pipeline
```

Create `.env` from `.env.example` and fill the project settings there. Then use this prompt.

## Recommended Prompt

```text
Use the dbt Analytics Engineer skill (`agentic-dbt-pipeline`).

Act as a Principal Data Engineer. Design the dbt project to be modular, idempotent, scalable, testable, cost-efficient, and safe for downstream consumers. Treat data asset development like software engineering.

Build the dbt project using the settings from `.env`.
Run the full pipeline from source discovery through final delivery.

Read any project knowledge files I provide, such as `AGENT_KNOWLEDGE.md`, `docs/dbt_knowledge.md`, `docs/business_rules.md`, `.agents/project_knowledge.md`, and `reports/agent/CONTEXT_TREE.md`. Apply `project_rules` from my prompt first, summarize which knowledge was used in each phase plan/report, and ask before persisting new dbt knowledge from chat into project files.

Use the skill's built-in knowledge layer for reusable dbt, big data, warehouse optimization, semantic layer, Power BI, privacy, and validation standards. Use project knowledge only for local/domain overrides. Do not copy large external documentation into the project; use official documentation only when current version-specific behavior is needed.

If `.env` is missing, create it safely from `.env.example` with placeholder values only, ask me which dbt profile this pipeline should use by listing available profiles from `~/.dbt/profiles.yml` with profile name, adapter, database or database-equivalent, and profile schema, stop before discovery or dbt commands, and ask me for DBT_DOMAIN, DBT_PROFILE_NAME, and DBT_SOURCE_SCHEMA. You may also ask for optional DBT_BUSINESS_DESCRIPTION when more business context would help analytics insight reporting, but do not require it for discovery. Do not create discovery reports while `.env` is missing or placeholder-only. Do not fill `.env` from a profile, profile target schema, warehouse schema, previous run, example, or guess. Do not use DBT_DOMAIN or DBT_BUSINESS_DESCRIPTION directly as project folders, model folder slugs, warehouse schema prefixes, database names, or source names; derive those from source/project evidence unless I explicitly override them. Do not say you will resolve the active profile or run PostgreSQL, Redshift, Snowflake, BigQuery, Databricks, or any adapter-specific discovery until I choose `DBT_PROFILE_NAME`. Do not search the repository, inspect terminal output, infer, suggest, or summarize values from other workspaces or previous runs. Do not choose a profile automatically.

First, perform lightweight read-only project discovery only: inspect source schemas/tables, write `reports/agent/discovery_report.md` and `reports/agent/requirements.md`, update `reports/agent/PIPELINE_STATUS.md` and `reports/agent/CONTEXT_TREE.md`, summarize what you conclude about the data project, and ask whether I want to add requirements. The requirements file must capture source-derived requirements, evidence, confidence, recommended defaults, open questions, user-provided requirements, and deferred or blocked scope. Before discovery, resolve the active dbt profile from `.env`, read that profile's adapter from `~/.dbt/profiles.yml`, announce the selected profile and adapter, and use only that adapter's discovery path. Do not call AWS, Redshift, PostgreSQL, Snowflake, BigQuery, Databricks, cloud identity checks, warehouse connectors, metadata queries, or Model Context Protocol discovery servers before `.env` and the selected dbt profile adapter are resolved. Do not query AWS, Redshift, or any other warehouse unless the selected dbt profile uses that adapter or I explicitly ask you to change profiles. If the configured source is missing, empty, inaccessible, ambiguous, mismatched, or appears wrong, stop after metadata-only candidate listing, recommend the likely replacement with evidence, and wait for my approval before changing database, dataset, catalog, schema, table, tenant, client, domain, environment, assumption, `.env`, profile settings, profiling candidate tables, writing discovery reports, or continuing discovery. Keep discovery output focused on source data, entities, relationships, data quality, candidate models/metrics, and open modeling decisions; keep setup details out of the discovery summary except for a short inputs-used note. Include a `Recommended Medallion Direction` section that covers sources, bronze/staging, silver/intermediate, and gold/marts with recommendation, evidence, not-ready items, and approval needs for each area. During discovery, create a Mermaid entity relationship diagram when credible relationships exist, and create any other necessary Mermaid diagrams such as source inventory, candidate business process flow, or high-level medallion direction when they help review the project. Do not fully design every layer upfront; run focused discovery again before sources, bronze, silver, gold, semantic, evaluator, documentation, and analytics insight reporting phases.

Use Mermaid for every diagram. For entity relationships, use Mermaid `erDiagram`. Verify every Mermaid diagram you add or change is visible/parseable, and record the result in the phase report.

Use full wording in all user-facing plans, reports, summaries, diagram notes, and final handoffs. Avoid shorthand such as primary key abbreviations, foreign key abbreviations, entity relationship diagram abbreviations, documentation abbreviations, repository abbreviations, and continuous integration abbreviations unless quoting a command, filename, package name, environment variable, or official tool name.

Every report, final handoff, business-facing presentation, and Power BI report plan must be actionable, not a data dump. Include five report pillars when relevant: context and strategy, key performance indicators, trend analysis and variance, insights and attribution, and recommendations and next steps. If a pillar is not supported by validated data yet, show it as deferred or needing business input with the reason. Do not invent targets, benchmarks, root causes, or recommendations without evidence. For Power BI reports, use a fixed interactive canvas standard on main pages: header/navigation with report title, page title, last refreshed timestamp, reset filters, and page navigation; prioritized executive key performance indicator cards at the top; visible primary slicers; trend and comparison visuals in the middle; matrix/detail visuals at the bottom or on a details page; and smart tooltips or drill-through pages where safe and supported. Analyze the maximum useful supported key performance indicators, place only the highest-priority measures in the top executive row for readability, and put supporting key performance indicators in a scorecard/details area or Report Information page. Include a Report Information, Report Settings, or About This Report page with report purpose, audience, data source, refresh details, page guide, key performance indicator definitions, filter definitions, caveats, privacy handling, validation summary, and open decisions. Document any missing canvas element with the reason.

After I answer at the discovery checkpoint, run project setup and configuration automatically: write/update `AGENT_PLAN.md` with the setup phase marked as automatic setup-only, create the local dbt scaffold if needed, install missing dependencies, run `dbt debug`, run `dbt deps`, run `dbt parse`, and write the setup report. Interpret my response by the active workflow checkpoint, not by general intent. Discovery checkpoint approval only confirms the source and automatic setup. It does not approve source YAML generation, bronze/staging, silver/intermediate, gold/marts, semantic layer, evaluator, documentation, analytics insight reporting, presentation layer, continuous integration, Agents Schema, commits, pushes, or source switching. Stop and ask first if required settings are missing, the selected profile is unsafe or failing, existing project files would be overwritten, warehouse objects would be created or replaced, credentials are needed, or I explicitly disabled automatic setup.

During project setup and configuration, perform profile target schema hygiene and write the result into `reports/agent/setup_report.md` and `reports/agent/PIPELINE_STATUS.md`: active profile, adapter, database, target schema, source schema, whether the target schema is safe, and any required mitigation. Treat unsafe target schema routing as a setup blocker, not an optional follow-up.

Treat the configured source schema and source tables as read-only and immutable for the entire run. Never run `UPDATE`, `INSERT`, `DELETE`, `TRUNCATE`, `MERGE`, `CREATE`, `DROP`, `ALTER`, backfill, repair, or status-changing commands against source. If I ask to change source data, such as marking records complete, implement the requirement only in dbt framework artifacts in non-source schemas, such as derived model columns, flags, mappings, tests, audits, or snapshots, and state that the source was not changed.

After every bronze/staging, silver/intermediate, and gold/marts build, run warehouse data validation queries before moving to the next layer. Verify row counts, expected-empty evidence, grain, keys, relationships, row-count movement, date coverage, status/category distributions, important measures, mapping coverage, and privacy exposure. Write `Data Verification Results` into the layer report, share the important results with me, and stop when a model expected to contain data is empty or any validation issue is unexplained.

For gold/marts, semantic layer, analytics insight reporting, presentation layer, and final delivery, define key performance indicators with business meaning, source model, grain, numerator, denominator, filters, time field, dimensions, caveats, validation evidence, approval status, and metric verification status. During analytics insight reporting, discover key performance indicators with a generic, domain-neutral framework: classify tables, detect grain, detect count/amount/quantity/status/date/ranking candidates, map candidates to volume, value, average value, ratio, funnel, conversion, status mix, time trend, cycle time, aging, ranking, utilization, quality, retention, or exception archetypes, then score confidence as `HIGH`, `MEDIUM`, `LOW`, or `BLOCKED`. Do not create key performance indicators from column names alone. Defer or ask for approval when definitions are ambiguous; do not silently implement advanced metrics. For every implemented key performance indicator, reconcile expected versus actual numerator, denominator, filter logic, and final result from upstream logic to gold/marts, semantic metrics, and Power BI/DAX/report measures. Stop before semantic layer, analytics insight reporting, presentation layer, or final delivery when a metric does not reconcile, including cases where a denominator accidentally equals the numerator but the business definition expects additional states.

After marts, semantic layer, evaluator, and documentation are complete, run analytics insight reporting before presentation work. Read `references/analytics-insight-reporting.md` and `references/kpi-discovery-framework.md`, write/update `AGENT_PLAN.md`, get my approval, and produce `reports/agent/analytics_insight_report.md`, `kpi_discovery_matrix.md`, `reporting_catalog.md`, `kpi_catalog.md`, `dashboard_spec.md`, `insight_backlog.md`, `reporting_readiness_scorecard.md`, and `analytics_insight_reporting_report.md`. Do not create fake insights, suggest charts just because data exists, or build presentation artifacts in this phase. Every key performance indicator and report candidate must map to validated marts or semantic metrics. Promote only `HIGH` confidence and user-approved `MEDIUM` confidence key performance indicators into `kpi_catalog.md`, semantic metrics, or Power BI DAX; defer `LOW` and `BLOCKED` candidates to `insight_backlog.md`. Clearly separate trusted outputs from uncertain or deferred outputs. Maximum means maximum useful business insight supported by validated data, not maximum number of dashboards.

After analytics insight reporting is complete, ask whether I want a presentation layer before closing final delivery. Use `dashboard_spec.md`, `kpi_discovery_matrix.md`, `kpi_catalog.md`, `reporting_catalog.md`, `insight_backlog.md`, `reporting_readiness_scorecard.md`, and `analytics_insight_report.md` as the scope contract. Do not invent pages, key performance indicators, visuals, or business scope that bypass analytics insight reporting unless I explicitly override it. If I approve a presentation artifact, design it like a professional enterprise report: infer the richest useful page set from validated facts, dimensions, semantic metrics, source profiling, and data quality evidence; include context and strategy, executive overview, key performance indicators, trend analysis and variance, insights and attribution, financial or value views, operations or activity views, entity performance, segmentation, exceptions, recommendations and next steps, and detail or drillthrough pages only when supported by the data. For Power BI, apply the fixed interactive canvas standard to every main page: header/navigation, prioritized executive key performance indicator card row, supporting key performance indicator coverage, slicers, trend/comparison middle layer, detail layer, tooltips, drill-throughs, and a Report Information or Report Settings page when safe and supported. Maximize validated, decision-useful information, not every available column. Do not ask me to design every page or visual, but do ask for decisions that affect business meaning, privacy, cost, refresh behavior, or downstream usability. Treat presentation content as two visual layers: domain key performance indicators and a standard time showcase. If validated facts have usable date columns, the approved presentation artifact must include a `Trends` page or equivalent standard time showcase with last calendar year, year to date, last 12 months, by-year, and by-month visuals for primary facts. Discover time fields from gold facts, model YAML, semantic models, or mart SQL; do not hardcode field names from one domain. Use governed measures or reportable filters where they exist, relate facts to the date table or `time_spine_daily` when safe, disable Power BI automatic local date tables for generated models, validate every time visual number with SQL, and record each exact verification query in `reports/agent/presentation_report.md`. Verify every key performance indicator visual and DAX/report measure against gold or semantic SQL, including expected numerator, actual numerator, expected denominator, actual denominator, expected result, and actual result. If I approve the presentation layer and do not specify another technology, default to a Power BI PBIP/TMDL project. Create a separate `presentation_layer` phase plan with page rationale, source models, measures, slicers, privacy handling, blocked visuals, and verification queries; build the approved artifact, validate it, and write `reports/agent/presentation_report.md`. Do not create dashboards, reports, slides, notebooks, or business intelligence artifacts unless I approve that follow-up work.

For Power BI PBIP/TMDL artifacts, use the bundled neutral PBIP template at `assets/powerbi/pbip_template/` as the default structural base by running `python scripts/generate_powerbi_pbip.py --name <safe_pbip_name> --display-name "<report display name>" --output-dir <powerbi_parent_folder> --project-root <project_root>`, then add project-specific gold tables, relationships, measures, pages, visuals, and validation evidence. Power BI measures must be generated only from `reports/agent/kpi_catalog.md`, validated dbt semantic metrics, or explicit user-approved requirements; do not invent Power BI-only key performance indicators, denominators, business flags, keys, or relationship shortcuts. Each generated DAX measure must map back to source key performance indicator name, dbt model, formula, time field, grain, allowed dimensions, confidence, caveats, and verification evidence. Use the official Microsoft Power BI Desktop project documentation at `https://learn.microsoft.com/en-us/power-bi/developer/projects/` and the linked semantic model/report folder pages when PBIP/PBIR/TMDL structure is uncertain, and record consulted docs in `reports/agent/presentation_report.md`. Do not depend on finding an existing local PBIP such as IHMS, ShopSphere, Hospital, or any nearby project. If you want to use a local PBIP as a reference, show me the exact path, explain what structural files would be inspected, get my approval, and reuse only structure/metadata patterns; do not copy source connections, business content, measures, relationships, page names, visuals, branding, logical IDs, lineage tags, `.pbi/` cache files, or source database names unless I explicitly approve. Run a validation loop before handoff: first actively check whether Power BI Modeling Model Context Protocol tools are available or installable, preferring the official Microsoft implementation `@microsoft/powerbi-modeling-mcp` from `https://github.com/microsoft/powerbi-modeling-mcp` and the startup command `npx @microsoft/powerbi-modeling-mcp@latest --start` when Node.js and `npx` are available. If `pbi-cli` is already installed or approved, use it only as an optional helper for DAX validation, semantic model audit, relationship checks, or report-layer inspection; it must not become the source of business truth. Then run static file checks, relationship ambiguity audit, Power BI Modeling Model Context Protocol `ConnectFolder` or `ConnectToPBIP` and model inspection when available, DAX smoke query, and Power BI Desktop open validation when available. Do not skip Model Context Protocol validation when the tools are installed or exposed; if available tools are skipped, mark presentation validation as FAIL. If the tools are not exposed but a tool/plugin/connector installation mechanism is available, request or recommend installing the exact Power BI Modeling Model Context Protocol connector/plugin before final validation. Record the tool availability check, install attempt or reason not installed, tool names used, and result in `reports/agent/presentation_report.md`. Run `python scripts/validate_powerbi_pbip.py <pbip_project_folder>` when available and fix every failure. Static checks must include root `.pbip` shortcut schema validation where report deliverables use the required `report` property and not unsupported `dataset`, the `.pbip` report path resolves to an existing `.Report` artifact folder, root-level Report `definition.pbir` exists, is non-empty, parses as JSON, and links to an existing `.SemanticModel` folder through `datasetReference.byPath.path`, legacy nested `definition/definition.pbir` is not used for enhanced PBIR, `definition/report.json`, `definition/version.json`, and `definition/pages/pages.json` exist, every page in `pageOrder` has a `page.json` and at least one `visual.json`, `.platform` `$schema` values match the supported Fabric git integration platform properties pattern with `config.version = "2.0"` and a stable `config.logicalId`, `definition/report.json` `themeCollection.baseTheme.reportVersionAtImport` presence/type/value as a non-empty string, defaulting to `"5.55"` unless a known-good project reference proves another value, no duplicate TMDL `lineageTag` values, no table with more than one `IsKey = True` column, no generator behavior that marks every `*_id` column as `IsKey`, no multiple active relationship paths between the same tables, no PostgreSQL partition anti-patterns such as `PgSchema`, unquoted server/database parameters, missing `Table.SelectColumns`, missing `Table.TransformColumnTypes`, or missing `PBI_ResultType`, a calculated measures/metrics table partition, TMDL table files with no Markdown code fences or invalid unindented loose Power Query `let`/`in` lines outside valid expression blocks, no bare M steps such as `AddedKey = Table.AddColumn(...)` at TMDL root, and no linguistic metadata content-type mismatch such as JSON `{ "Version": "1.0.0" }` inside XML-typed metadata. Treat Power BI Desktop errors such as `ReportDefinition: Required artifact is missing`, `RequiredArtifactMissing: Path: definition.pbir`, `RequiredArtifactMissing: ArtifactName: ReportDefinition`, `.platform` `ObjectNotPerSchema` failures such as "Required properties are missing from object: config", invalid TMDL indentation around Markdown fences, linguistic metadata errors such as `does not comply with the Xml content-type`, or blank report pages with no visuals as failed static validation. Before generating Power BI relationships, verify in dbt that every one-side dimension key is unique and not null; composite business keys must use a tested surrogate key, not a repeated partial natural key. Fix and repeat until validation passes. Do not report the presentation layer as complete unless `presentation_report.md` and `PIPELINE_STATUS.md` show PASS with evidence, or clearly show BLOCKED/NOT RUN for unavailable required checks.

The presentation-layer recommendation and my decision are required for full pipeline final delivery. If I have not answered the presentation question, set status to `Analytics insight reporting complete - presentation decision pending`, not `Delivery complete`. If I approve a presentation artifact, validation must be completed before final delivery; if validation fails or cannot run, mark presentation and final delivery as blocked with evidence instead of complete. If you cannot produce the recommendation, mark it blocked or skipped with the reason in the final report, pipeline status, context tree, and final response.

Before final delivery, perform an advanced data-engineering review covering source lock, schema hygiene, layer validation, grain, tests, data quality, privacy, key performance indicators, semantic layer, evaluator, documentation, analytics insight reporting, presentation-layer recommendation, and operations.

Before each non-setup build phase, write/update `AGENT_PLAN.md`, explain in Markdown what you will build, and wait for my approval before implementing that phase. Treat each approval as checkpoint-scoped only. After a phase completes, write the phase report, share validation results, write/update `reports/agent/NEXT_PHASE_PROMPT.md` with the exact prompt for the recommended next phase, then show me a chat control-panel summary before asking approval. The chat summary must explain what was completed, what passed/warned/failed, what is recommended next, what the next phase will and will not include, and paste the exact next-phase prompt in chat. Do not only say "the prompt is in NEXT_PHASE_PROMPT.md." Ask approval through a native interactive question when the runtime supports it. Use the question "Do you want me to run this next-phase prompt as written?" with "Yes, run this prompt" as the recommended option, plus "Tell me what to change" and "Not now" when available. If interactive questions are unavailable, use the text fallback: "Do you want me to run this next-phase prompt as written? Reply Yes to proceed, or tell me what to change." Natural replies such as Yes, Proceed, Approved, Continue, Run this prompt, Looks good, or Go ahead approve only the displayed next-phase prompt for the active checkpoint. If I ask for any change to scope, models, key performance indicators, privacy, schemas, validation, materialization, or files, revise `AGENT_PLAN.md` and `reports/agent/NEXT_PHASE_PROMPT.md` before proceeding. Do not treat silence as approval and do not require exact phrases such as approve sources, approve bronze, approve silver, or approve gold after the next-phase prompt has been shown.

When I approve a displayed next-phase prompt, do not run `reports/agent/NEXT_PHASE_PROMPT.md` in isolation. First reload the phase context bundle: `SKILL.md`, `prompt.md`, phase-specific references, `AGENT_PLAN.md`, `reports/agent/PIPELINE_STATUS.md`, `reports/agent/CONTEXT_TREE.md`, `reports/agent/requirements.md` when present, the latest relevant phase report, `reports/agent/NEXT_PHASE_PROMPT.md`, and project knowledge files when present. Then execute only the approved next phase.

In each discovery summary and phase plan, recommend the best next path with evidence, show what looks right, what is not ready yet, confidence about proven vs uncertain items, and what needs my approval. Do not ask me to design everything from scratch.

When sensitive fields or unclear coded fields appear, propose the safe default instead of only asking me what to do. For direct identifiers such as patient names or medical record numbers, recommend excluding, masking, or hashing them from gold/marts by default. For ambiguous, placeholder, abbreviated, generic, or poorly named fields, recommend passing them through bronze/staging as raw unmapped source fields, deferring mapping seeds until definitions are provided, and excluding them from gold/marts unless I approve raw audit exposure. Do not rename unclear fields unless I provide definitions or explicitly ask for suggested names; if I ask for suggestions, analyze values, propose candidate names with confidence, and wait for my approval of the exact final names before changing SQL or YAML.

In each phase plan, include a Data Engineer Decision Check covering grain, keys, joins, bridge tables, mappings, metrics, privacy, materialization, tests, and validation evidence. Ask me before guessing any decision that affects business meaning, privacy, correctness, cost, or downstream usability.

If you cannot properly understand source tables, relationships, business processes, required metrics, data quality rules, required output models, or reporting needs, do not assume. Ask me for the missing business meaning or approval, and defer dependent models, tests, metrics, semantic definitions, or presentation outputs until I confirm.

After each completed or blocked checkpoint, write/update `reports/agent/<phase>_report.md`, `reports/agent/PIPELINE_STATUS.md`, `reports/agent/CONTEXT_TREE.md`, and `reports/agent/NEXT_PHASE_PROMPT.md` with what was done, what passed, warnings/failures/skips, assumptions, user decisions, phase outputs, report links, open decisions, and the exact next-phase prompt. Also share a short chat result summary with current checkpoint, status, report path, goal, what was completed, what was built or changed, validation, included scope, not-included scope, open decisions, next checkpoint, next goal, next includes, next does not include, known caveats, files/reports that will be created next, the exact next-phase prompt pasted in chat, and the interactive approval question or text fallback.

Ask me only when required `.env` values are missing, credentials or secrets are needed, automatic project setup hits a safety gate, a business rule is unclear, non-setup phase build approval is needed, or before committing, pushing, or changing schema behavior.
```

## Optional Project Rules

Add this only when the project has business-specific rules, mappings, joins, or privacy requirements.

```text
Project rules:
- Field mappings:
  - <source_table.source_column> -> <target_column>: <meaning/rule>
- Joins:
  - <left_table.column> -> <right_table.column>: <relationship>
- Metrics:
  - <metric_name>: <definition, grain, filters>
- Exclusions:
  - <tables/columns/records to ignore>
- Privacy:
  - <personally identifiable information / protected health information handling, masking, or exclusion rules>
- Naming:
  - <custom naming conventions>
- Special instructions:
  - <anything else the agent must follow>
```

If a rule is unclear, the agent should ask before modeling it.
